## 2. Code ground truth (verified against `main_cost_aware.py`)

- EMA: `alpha = 2/(W+1)`, `decay = (1-alpha)^Δt`, default window `E2E_EMA_WINDOW=240s` (half-life ≈ 80 s). Matches Algorithm 1 in Ch4.
- Scale-up: `per_request_tps_ema < E2E_MIN_TPS (10.0)` → next tier. Scale-down: EMA ≥ threshold AND `MEASURED_THROUGHPUT[lower] / max(ar_ema, 1.0) ≥ 10 × 1.5`. One tier per decision, ordered by `tier_order`.
- Sampling: background loop every 1 s computes per-request tok/s = tokens/wall-time over all in-flight requests (queued requests contribute 0); scaling checked every 10 s (`SCALING_CHECK_INTERVAL`).
- Safeguards: directional cooldowns (`E2E_COOLDOWN`, `E2E_COOLDOWN_DOWN`, both default 300); recent-activity hysteresis (`E2E_RECENT_ACTIVITY_WINDOW`, default 30 s — inflates effective concurrency to 1e6 to fail the viability check); EMA reset + seed at T_min on first token after a scale; `last_scale_time` also resets at first token.
- **Swap order is stop-old-THEN-start-new** (single host, resource contention). Rollback restarts old config if the new container fails health check (90 retries × 2 s async; 30 × 2 s in the sync `Container.start`).
- **Client responses are NOT streamed**: the proxy consumes the backend SSE stream internally and returns a buffered JSON chat completion; the request's `stream` field is ignored. Thesis now states this honestly (§4.1 ①, §4.6, Ch6 future work).
- **`E2E_SCALE_DOWN_CONCURRENCY` (5.0) is an inert knob**: set by `scaling_demo.py`, read and logged (`/status`, `DEMAND_CHECK`, `INIT`), but used in NO decision path. It was removed from Appendix B. Tests import it only as a convenient constant.
- `hardware_configs.json` (the real file) uses `"memory": "200g"` for all tiers (benchmark allocations). The thesis table/appendix show production allocations 4g/8g/16g; §5.3.5 ("Note on Memory Allocations", `\label{subsec:memory_note}`) discloses this. **User preference: keep the 200g low-profile** — Appendix A shows the production values and cross-refs §5.3.5 without repeating the number.
- Scaling demo (`benchmarks/scaling_demo.py`) env: COOLDOWN=60, COOLDOWN_DOWN=240, EMA_WINDOW=30, MIN_TPS=10, RECENT_ACTIVITY_WINDOW=**15** (Appendix B fixed from 30). Six phases, 1800 s: (1) 1 worker @3 rpm 240s, (2) 12 workers 240s, (3) 35 workers 300s, (4) 55 workers 300s, (5) 6 workers 360s, (6) 1 worker @**2** rpm 360s (Appendix B fixed from 3 rpm). Workers are closed-loop (one outstanding request each) — this is still NOT stated explicitly in §5.6.1 (open item).

- Benchmark quirk (now honestly described in §5.2/§5.3.4): reported throughput is the **mean of per-round values over completed rounds under a 120 s per-batch budget**, not total-tokens/total-wall-time. cpu_4's peak (92.2 @ batch 32) comes from a budget-truncated batch whose raw totals equal batch 16's.
